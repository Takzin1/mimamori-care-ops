# CareOps Human-Centered Operations OS — 設計書

最終更新: 2026-11-15 ／ 対象ブランチ: `claude/kind-franklin-t91s96`（PR #74 に積み増し）

安否確認の「あと」に起きる **確認 → 判断 → 担当 → 引継ぎ → 支援完了** を、取りこぼしなく・
誰の責任かを曖昧にせず・後から検証できる形で管理するための設計です。
本書は英語の既存ドキュメント（[Architecture](careops-architecture.md) /
[Workflow](careops-workflow.md) / [Security](careops-security.md)）を置き換えず、
今回の段階で追加した部分をまとめます。

> 本リポジトリは未デプロイです。登場するデータはすべて合成データで、本番DBには触れていません。

## 1. 設計原則（人が中心）

| 原則 | 実装上の意味 |
|---|---|
| 判断するのは人 | 優先度・対応不要・担当・解決・クローズ・エスカレーション解除は、権限を持つ職員のコマンドでのみ変わる。システムが自動で行うのは「Case化（設定された通知種別のみ）」「重複通知の紐付け」「通知の送信」だけ |
| AIは下書きと整理まで | AI下書きは職員が承認した場合のみ対応履歴に入る。次の対応候補はルールベースで、優先度の値・医療的判断・緊急度を提案しない |
| 権限はサーバーで決める | テナント・施設・ロールはサーバー側の所属情報で判定し、リクエストの値は信用しない |
| すべて後から検証できる | 追記のみのイベント履歴、変更前後の監査証跡、証拠参照、設定変更・AI利用の監査ログ |
| 数字を誇張しない | 目標値は「仮設定」と明示し、分母を必ず示す。事故削減率・業務削減率などの効果指標は表示しない |

システムが **自動で行わないこと**: 確認済みにする／優先度を変える／担当を付け替える／
引継ぎを受領・取消する／解決・クローズする／エスカレーションを解除する／AI下書きを履歴に入れる。

## 2. 監査結果（着手前の状態）

再利用した既存資産（書き換えていません）:

| 既存資産 | 場所 | 今回の使い方 |
|---|---|---|
| イベントソーシングの状態機械・楽観ロック | `src/core/case-core.ts` | 規則を2点追加（§3-①）。既存履歴はそのまま再生可能 |
| `CaseService`（権限確認つきコマンド実行） | `src/application/` | すべてのCase操作はここを通る。迂回経路なし |
| RBAC・施設スコープ | `src/access/` | 担当者の「対応可能性」判定に同じ述語を再利用 |
| Transactional Outbox + `OutboxWorker` | `src/outbox/` | 再通知・未到達の可視化に再利用（配信キーで重複排除） |
| SLA評価 | `src/operations/sla.ts` | 期限超過通知・目標達成率の両方で同じ評価関数を使用 |
| 3種の永続化アダプタ（in-memory / SQLite / PostgREST） | `src/persistence`, `server/`, `src/careops/postgrest-stores.ts` | スキーマ変更なし。新しいマイグレーションは不要 |

見つかったギャップ（今回対応）:

1. 状態遷移の不変条件を網羅的に検査するテストがない
2. エスカレーション中のままクローズできてしまう
3. 担当者が退職・異動しても、そのCaseが誰にも気づかれない
4. 通知は1回きりで、誰も動かなくても再通知されない
5. 通知が届かなかったことが画面から分からない
6. 対応履歴（メモ）に証拠参照を付けられない（解決時のみ）
7. 「次に何をすべきか」が画面に出ない
8. 障害や夜間などの状況を再現して検証する手段がない
9. 目標の達成状況・通知の到達・AIの利用状況が集計されない

## 3. 実装内容（①〜⑨）

### ① 堅牢なCase状態遷移

- 状態: `NEW → ACKNOWLEDGED → TRIAGED → ASSIGNED → IN_PROGRESS ⇄ HANDOFF_PENDING → COMPLETED → CLOSED`、エスカレーションは状態ではなくフラグ。
- 追加した規則: **エスカレーション中はクローズ不可**（管理者が理由付きで解除してから）。
  コマンド検証にだけ入れ、イベント適用には入れていないため、過去の履歴は再生できます。
- 不変条件のモデルテスト（`tests/careops-invariants.test.ts`）: ランダムなコマンド列を多数実行し、
  「保存状態 = 履歴の再生結果」「版番号 = イベント数」「対応中のCaseには担当者がいる」
  「引継ぎ待ち ⇔ 引継ぎ先がいる」「拒否されたコマンドは状態を変えない」を毎手検査します。

### ② 施設単位の権限・データ分離

- 既存の施設スコープ（`TenantMembership.facilityIds`）とRLS/RPC（ADR 0016）をそのまま使用。
- 追加: `MutableTenantMembershipDirectory`（退職・異動・ロール変更をテストとSimulation Labで再現するための参照実装）。
- 検証: Simulation Lab の「施設間データ分離」6本 + 「担当不在」6本、
  実PostgreSQL/PostgRESTは既存の `tests/stack/*`（CI）。

### ③ 担当割当と引継ぎ

- 既存の「受領するまで責任は移らない」引継ぎを維持。
- 追加: 担当者・引継ぎ先の **対応可能性**（有効・対応ロールあり・その施設に所属）を判定し、
  一覧・詳細・ダッシュボードに「担当者不在」を表示。自動での付け替えはしません。

### ④ SLA管理とエスカレーション

- 期限（内部対応目標）は施設設定。既定値は **仮設定** で、施設が承認するまで画面に明示します。
- 追加: **再通知**。施設ごとに段階別の間隔（`repeatEveryMinutes`）と回数上限（`maxRepeats`、最大10）を設定。
  既定では「重大Caseの未確認」だけ10分ごと最大3回。
- 追加トリガー: `assignee_unavailable`（担当者・引継ぎ先が対応できない）。

### ⑤ 通知重複・未到達・担当者不在への耐障害性

| 事象 | 仕組み | 結果 |
|---|---|---|
| 同じ通知の再送 | `(sourceAdapter, sourceSignalId)` の一意性 | Caseは1件、再送回数を記録 |
| 同じ対象者の連続通知 | 未完了Caseへ `signal_linked` で紐付け（施設設定で無効化可） | Caseを乱立させない。優先度は自動で変えない |
| 期限チェックの多重・同時実行 | 配信キー（例 `sla:<case>:<stage>:<startedAt>[:rN]`）で冪等 | 職員への通知は1件 |
| 外部チャネルの障害 | Outboxの再送（最大5回）→ `dead_letter` | アプリ内通知は先に届き重複しない。未到達は管理者のダッシュボードに表示 |
| 担当者の退職・異動 | 期限チェックで検知し管理者・受付へ通知 | 候補として担当変更を提示（実行は人） |
| 職員の二重送信 | `clientRequestId` による冪等なCase作成 | 同じCaseを返す |

### ⑥ 証拠付きイベント履歴

- `add_note` に証拠参照（種別 + 参照ID、最大10件）を追加。解決時の証拠と合わせて
  `projectCaseEvidence` で時系列の「証跡一覧」として表示します。
- 証拠は参照IDのみを保持します（通話記録・訪問記録などの本体は保存しません）。

### ⑦ AIの状況要約と次の対応候補

- `src/careops/advisor.ts`（**ルールベース、LLM不使用**）。記録済みの構造化データ
  （状態・担当・期限・件数）だけから「状況の要約」と「次の対応候補」を作ります。自由記述は解釈しません。
- 候補はすべて既存コマンドに対応し、押しても通常の確認ダイアログが開くだけです。
  誰が実行できるかは、コマンド実行と同じ権限規則でサーバーが判定します。
- 優先度の値は提案しません。医療的判断・緊急度の判断に当たる文言を出さないことをテストで検査しています。
- 既存のAI下書き（要約・申し送り・事実抽出）は従来どおり、原文との照合と職員の承認が必須です。

### ⑧ 合成データによる Simulation Lab

- `src/careops/simulation/`。シナリオごとに **使い捨ての環境** を作り、製品と同じ
  `CareOpsPlatformService` を、仮想時計・変更可能な所属情報・障害を起こせる通知チャネルの上で動かします。
- 52シナリオ（要件は30以上）:

| カテゴリ | 本数 | 例 |
|---|---:|---|
| 通常 | 8 | 標準フロー、引継ぎ、辞退と担当変更、再開、権限 |
| 夜間 | 6 | 夜勤1名でのSOS、再通知の上限、日付またぎ、早番への引継ぎ |
| 未応答 | 6 | 未応答通知の職員判断、誰も確認しない、着手しない |
| 連絡失敗 | 4 | 外部チャネルの一時障害・恒久障害、家族に連絡がつかない経過の記録 |
| 担当不在 | 6 | 退職、異動、引継ぎ先不在、ロール変更、管理者不在 |
| 多重通知 | 7 | 再送、連続通知の紐付け、二重送信、期限チェックの多重実行 |
| 施設間データ分離 | 6 | 他施設・他法人、施設IDの偽装、異動後のアクセス |
| AIと人の承認 | 5 | 承認前は履歴に入らない、AI停止中の業務継続、未照合の記述 |
| 同時操作 | 4 | 同時割当、古い画面、受領と取消の競合、二重承認 |

- すべてのシナリオの最後に構造的な不変条件4項目を自動で再検査します。
- 同じシナリオを in-memory と SQLite の両方で実行し、観測される経過が一致することをテストしています。
- 検出力の確認: 5種類の欠陥（エスカレーション中のクローズ許可、通知の施設判定の削除、
  再通知の上限撤廃、施設をまたぐ割当の許可、重複紐付けの無効化）を一時的に入れ、
  いずれも該当シナリオが失敗することを確認しました（欠陥は取り除き済み）。

### ⑨ 運用指標ダッシュボード

`GET /analytics`（分析画面）に追加:

| 指標 | 定義 | 注意 |
|---|---|---|
| 内部対応目標の達成状況 | 段階ごとに 対象／目標内／超過／目標内で未完了、達成率 = 目標内 ÷（目標内 + 超過） | 期間末時点の履歴で評価。判定対象がなければ率を出さない。仮設定の目標を含む場合は警告を表示 |
| 職員への通知の配信 | 期間内の配信完了、うち再通知、種別ごと、現在の未到達（再送中・配信不能・送信待ち） | 管理者・監査担当のみ。「配信」は既読を意味しない |
| AI支援の利用 | 生成・失敗・承認・修正して承認・却下・確認待ち（監査ログ由来） | |
| 担当の状態 | 現在、担当者・引継ぎ先が対応できないCase数 | |

既存の指標（通知とCaseの区別、所要時間の中央値/P90、引継ぎ、頻度）は変更していません。

## 6. デモ

```bash
npm run careops:local
```

1. `http://127.0.0.1:8787` を開く → **「Simulation Lab（合成シナリオの検証）を開く」**
2. カテゴリを選んで実行 → シナリオごとに、職員の操作・時間経過・障害の注入・検証結果が時系列で表示されます
3. ログイン（合成の職員を選択）して、通常の画面で同じ機能を操作できます
   （Case詳細の「状況の要約」「次の対応候補」「証跡一覧」、ダッシュボードの「担当者不在」「通知未到達」、分析画面の運用指標）

Lab の実行はサーバーのデータベースに一切書き込みません（E2Eで検証）。コマンドラインでは:

```bash
npm run sim -- --category night -v          # 夜間のシナリオを経過つきで表示
npm run sim -- --store sqlite --json out/sim.json
```
